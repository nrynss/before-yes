## Probes (scratch tests, not committed)
- **Cap race:** 8 concurrent uncached `POST /api/checks` at cap 1, run 3 times under `-race`. Each run gave exactly one 202 and seven 402s. The reservation holds at the cap edge.
- **Scrub:** `scrub()` given a `job.Failure` whose text holds:
  - (a) a host body truncated by `snippet()` at 300 bytes, with the cut falling inside the key. **The key prefix survived.**
  - (b) a JSON-escaped echo (`\/`). **The whole key survived.**
  - (c) a URL-encoded echo. Redacted only because the fragment before the first `/` happened to be short. It was not matched as the key.

## What holds
- **Key storage.** Keys live only in the per-job client closures. `VisitorKeys` redacts itself in `String`, `GoString`, `LogValue` and `MarshalJSON`. Headers are not logged. Keys never go in a URL or query string. `Gathered.Notes`, which can hold Tavily extract error text (`storepage.go`), is not persisted (it is not in `Evidence` or `Stats`), so that path does not reach the DB.
- **Both or neither.** Holds, and invalid input gets a fixed message that does not quote the key.
- **Isolation.** The visitor pipeline uses new `model.Client` and `tavily.Client` instances (reader, judge, entail, and the gatherer search/extract, which alternatives also use) and a `VisitorMeter`. `Checks` is nil. The struct copies share only read-only settings maps, the App Store client and the caches.
- **Cap order.** The hold is reserved before `StartKind`, and so before any paid call. The 402 carries the contract body and `pool: daily_checks`. A successful job books with `Done`. A failure or panic releases with `Fail`. A `StartKind` error releases.
- **Shared meter.** The main check is reserved once, and alternatives go through `Pipeline.Checks`. `checkCapWiring` refuses mismatched or half-set wiring. That is correct.
- **TTL hold after a restart.** Acceptable: it only makes the cap stricter until the TTL lapses, and nothing is booked.
- **checks.go edit.** Minimal and justified. It adds a wiring check, admit/wrap/release, and passes the pipeline as a parameter.

## Findings

### Medium
- **M1: the key-echo scrub misses partial and encoded echoes.** `scrub` does only exact `strings.ReplaceAll`. Both clients put the host body into the error through `snippet()`, which cuts at 300 bytes, so a key that straddles the cut leaves its prefix in the job record, the WAL and the `GET /api/checks/{id}` error. A JSON-escaped echo (`\/`, `\u00xx`) or a URL-encoded echo also passes untouched. The brief asks for partial and encoded echoes to be covered.
  - *Fix direction:* for a visitor job, do not carry host body text into the failure at all, and replace the message with a fixed sentence for its code. Or at least also redact the escaped and encoded forms and any trailing prefix of the key of 8 or more characters.
  - *Pin:* a test with a truncated echo and an escaped echo.
- **M2: a panic in a visitor job is not scrubbed.** `wrap` releases the hold on a panic but does not recover, so Keel's runner records the panic value and stack, and stores or logs them unscrubbed. No current panic carries a key, so the risk is latent. The PR describes scrubbing as complete. Recover in `wrap` for visitor jobs and return a scrubbed `check_failed`, or document why that is out of scope.

### Low
- **L1: half-pair validation comes after the card cache.** `admit` runs after the cache hit, so a malformed visitor header pair on a cached title gets 200, not 400. docs/api.md puts validation (step 2) before the cache (step 3). Harmless, but it does not match the contract. Validate the headers with the body.
- **L2: docs/api.md has no line for `X-Token-Factory-Key` or `X-Tavily-Key`.** Documentation, so the orchestrator can close it.
