## Round-1 findings
- **M1: fixed.** `live` now needs `latestIndex >= savedAt` and `newer(candidate, saved)`: a later stage, or the same stage with `current >= saved.current`. A replayed 5 or 6 after a saved 7 of 9 is held back, and 7 and 8 go through. The new Playwright spec replays 5, 6, 7, 8 and checks that the count never drops and that the first two reads stay at 7.
- **L1: hardened.** `report` defers `recover()`. `TestProgressHookPanicRecovered` panics on the first call, from a goroutine, and checks that a second report still reaches the hook.
- **L2: still accepted.**

## Attacks on the fixes (no finding)
- **Can a terminal event be suppressed?** No. `done`, `error`, `cancelled` and `interrupted` are handled by the `$effect` on `stream.status`, which re-reads the check and routes or shows the notice. That path never reads `live`, `saved` or `newer`. The rule only picks which progress text is shown, so done always wins. An error snapshot carries no stage (`snapshot.ts` keeps progress only for queued and running), so it cannot pin an old stage.
- **Is the stage order correct and complete?** Yes. The server emits only `gather`, `read`, `judge` and `alternatives` (`checks.go`, `gather.go`, `read.go`). The rank list matches that order. `queued` carries no stage, and an unset or unknown saved stage ranks -1, so any real stage beats it.
- **Is a newer check or a changed total blocked wrongly?** No. `start()` resets `saved` and makes a new stream for each attempt. The comparison uses `current` only, and within one check `total` is fixed per read pass. A saved stage with no `current` (gather, judge, a cache hit's read, or a zero-total read) lets any frame in the same stage through. The only frame that is held back is a same-stage frame with no `current` when the saved one has a count. The server never sends that within one check, since a cache hit and a counted read cannot both happen.
- **Were the specs weakened?** No. Under the new rule, a saved `read` 3 of 9 correctly outranks the later `gather` frame these two specs push first, so they now start from a stage-less running snapshot. They still check gather, then read, then judge, and the reconnect reread of 7 of 9. "page opened mid-read…" still runs against the unchanged read fixture.
- **Does the recover swallow anything or skip a count?** No count is skipped. `finished` is incremented before `report`, and `progMu.Unlock()` still runs, because the panic is recovered inside `report`. `work`'s hook unlocks with a defer, so a panic in Keel's `report` cannot leave `mu` held. Only the display of that one step is lost.
