## Attacks on the fix

- **Crash or exit releases the lock.** Pin: a child process takes the lock; the parent gets `ErrMeterBusy`; after `SIGKILL` of the child the parent takes the lock at once. `flock` belongs to the open file and the kernel drops it when the process dies. The leftover `spend.db.lock` file is harmless: only the lock matters, not the file's existence, so a stale file never blocks a start.
- **Docker and the deploy filesystem.** The deploy is a Linux container on the Hetzner tenant with `data_dir` on a local volume (ext4/overlay or a bind mount), where `flock` works. `flock` is unreliable only on network filesystems (old NFS), which the deploy does not use.
- **Tests and the check flow.** The race suite and `tools/check.sh` pass; tests that build cores use their own temp `data_dir`. `flock` is per open file description, so even two cores in one process exclude each other, which is the intended behaviour.
- **Lock before meter, closed on every error path.** Each early return after the lock calls `c.Close()`, which closes the lock file.
- **Titles starting with `-`.** See A6.
