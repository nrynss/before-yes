| ID | Level | Finding | Resolution |
|---|---|---|---|
| L1 | L | `PoolConfig.Period` is caller config and the package never binds `PoolTavily` to `cost.MonthlyUTC`, so a caller can open the Tavily pool with the zero period and turn the 1,000-credit monthly allowance into a lifetime one. The comment in `PoolConfig.Period` tells the caller to pass `cost.MonthlyUTC`, but nothing enforces or defaults it. | Faithful to the task's split: T2.5 owns the ceilings and windows, and the meter's own test opens Tavily with `cost.MonthlyUTC`. T2.5's settings must carry the period, and the wiring task should pin it. No change here. |
| L2 | L | Keel's cost store and the sqlite migration runner log to `slog.Default`, and `spend.Config` offers no logger, so every `Open` writes "sqlitestore: opened" plus, on a cold file, six "sqlite: applied migration" lines per pool that the meter cannot route or quiet. | Cosmetic. No secret, prompt or price beyond the configured limit is logged. T4.4's config wiring can set `slog.SetDefault`. No change here. |
| L3 | L | The doc "The hold stands while work runs" is bounded by Keel's 10-minute `ReservationTTL`, which the meter neither exposes nor names. Once the stored expiry passes, `Status` reports the headroom back while the call still runs, and a second `Open` purges the hold. A call longer than the TTL can let another call reserve the same headroom, and both settles can then push booked spend past the ceiling. | Keel's design (a dead process must stop holding budget) and the project's calls run in seconds. Worth a doc sentence, or a `ReservationTTL` in the meter's config if T3.x ever has a slow call. |
| L4 | L | A refused second pool still leaves the first pool's tables behind: opening `PoolTavily` with a `_owner` namespace fails the whole `Open` with `coststore.ErrInvalid`, but the already-opened `cost_model_*` schema, its migration ledger and the ceiling row are on disk. The refused namespace itself leaves nothing. | Inert, and Keel documents the same shape for a cancelled open; a corrected open reuses the tables. Recorded so the wiring task does not read the failure as a clean file. No change. |
| L5 | L | There is no `Once`/idempotency option: two `Spend` calls with the same kind and ref book two charges and `Spent(ref)` sums them. Keel's `Meter.Call` has `Once`, which the seam does not surface. | The task defines the ref as the check id and several calls legitimately share it, so dedupe is not in this contract. A retried pipeline step overstates the ledger rather than overspending it. Add it when T3.x has a resume path, not now. |

Attempts that failed to break the work:

- Forcing a double release: a trigger that refuses the charge insert after a successful settle did not make the deferred release delete a hold the settle had already consumed; the reservation table stayed empty and the spend stayed booked.
- Forcing a release failure: the work's error and the release error both survive in the returned chain, and the hold stands, exactly as the doc says.
- Forcing a settle failure: the overflow refused before any write and still freed the hold.
- A panic in work: the deferred release ran while unwinding, no hold and no charge survived, and the panic continued past `Spend`.
- Boundary and overshoot: `estimate == remaining` is admitted and `remaining + 1` refused; an estimate of zero followed by a large measured price books past the ceiling, which is Keel's documented "a booking records what a call actually cost" and not a meter defect.
- Namespace collisions: the two pools cannot be aimed at one namespace, and a wrong-way reopen is refused by the stored denomination.
- Zero-value and closed meters, unknown pools, bad periods and negative limits all refuse without a panic and without a meter.
- The author's tests left the negative-price, settle-failure, charge-failure, release-failure, panic and concurrency paths uncommitted; my probe covered all of them and found no defect.
